# B01 — Discover 5 Unique Weak/Vulnerable Security Implementations

---

## Summary Table

| # | Weak / vulnerable implementation | Security area | Main risk | Recommended fix |
|---|---|---|---|---|
| 1 | Password login without multi-factor authentication | Identity and access management | Account takeover if passwords are guessed, reused, leaked, or phished | Enforce MFA, especially for administrators and sensitive accounts |
| 2 | Weak password policy and no breached-password checking | Authentication | Users can create easily guessed or previously leaked passwords | Use minimum length, block common/breached passwords, and rate-limit login attempts |
| 3 | Sensitive cookies missing `HttpOnly`, `Secure`, or `SameSite` attributes | Web session security | Session theft or cross-site request abuse | Set secure cookie attributes and use HTTPS everywhere |
| 4 | Excessive user permissions / lack of least privilege | Access control | A compromised low-level account can access or modify more data than necessary | Apply role-based access control and review permissions regularly |
| 5 | Publicly exposed development or diagnostic information | Information disclosure | Attackers can learn internal paths, software versions, stack traces, or configuration details | Disable debug mode, restrict diagnostics, and sanitise error messages |

## Finding 1 — Login System Without Multi-Factor Authentication

### Description
A weak security implementation occurs when an application relies only on a username and password for authentication, particularly for privileged users such as administrators, staff, or maintainers. Password-only login is fragile because passwords can be reused, guessed, phished, intercepted on compromised devices, or exposed in third-party data breaches.

### Why this is vulnerable
Even a strong password policy cannot fully protect accounts if users reuse passwords or fall for phishing. Without multi-factor authentication, possession of the password is often enough to access the account. This creates a single point of failure in the authentication process.

### Example evidence to collect
For a real assessment, evidence could include:

- A screenshot of the account security settings showing no MFA option.
- A login workflow where only username and password are required.
- Documentation confirming MFA is optional or unavailable.
- A test account showing that sensitive features are accessible after password-only login.

### Potential impact
An attacker who obtains valid credentials may be able to:

- Access personal or organisational data.
- Modify account settings.
- Send messages or perform actions as the victim.
- Escalate access if the compromised account has administrative privileges.

### Recommended remediation
The system should enforce MFA for privileged users and strongly encourage it for all users. Safer options include authenticator apps, hardware security keys, and passkeys. SMS-based MFA is better than password-only authentication but should not be the preferred option for high-risk accounts.

## Finding 2 — Weak Password Policy and No Breached-Password Blocking

### Description
A weak password implementation allows users to create simple passwords such as `password123`, `qwerty123`, `letmein2024`, names, dates of birth, or other common patterns. The weakness is worse if the system does not check whether a chosen password appears in known breach lists.

### Why this is vulnerable
Attackers commonly use password spraying, credential stuffing, and dictionary attacks. If users can choose common or previously breached passwords, accounts become easier to compromise. A policy based only on character complexity, such as requiring one uppercase letter and one symbol, may still allow predictable passwords like `Password1!`.

### Example evidence to collect
For a real assessment, evidence could include:

- Attempting to create a test account with a weak password in an authorised environment.
- Password reset or registration rules showing only minimal password requirements.
- Absence of rate-limiting or lockout after repeated failed login attempts.
- Absence of breached-password warnings during registration or password change.

### Potential impact
Weak password handling can lead to:

- Compromised user accounts.
- Automated credential stuffing attacks.
- Increased helpdesk and incident response workload.
- Unauthorised access to sensitive data.

### Recommended remediation
Use modern password guidance:

- Require a reasonable minimum length, such as at least 12 characters for standard users and longer for privileged users.
- Block common and previously breached passwords.
- Allow password managers and long passphrases.
- Avoid forcing frequent password changes unless compromise is suspected.
- Add rate-limiting, account lockout, or risk-based login controls.

## Finding 3 — Insecure Session Cookies

### Description
Session cookies are used to identify authenticated users. A weak implementation occurs when sensitive cookies are missing protective attributes such as `HttpOnly`, `Secure`, and `SameSite`.

### Why this is vulnerable
Cookie attributes help protect session tokens from theft or misuse:

- `HttpOnly` reduces the risk of JavaScript accessing the cookie during cross-site scripting attacks.
- `Secure` ensures the cookie is only sent over HTTPS.
- `SameSite` helps reduce cross-site request forgery risks.

If these protections are missing, attackers may have more opportunities to steal or abuse session tokens.

### Example evidence to collect
For a real assessment, evidence could include:

- Browser developer tools showing session cookies without `HttpOnly`, `Secure`, or `SameSite`.
- HTTP response headers containing insecure `Set-Cookie` values.
- A controlled test environment showing cookies transmitted over unencrypted HTTP.

Example weak header:

```http
Set-Cookie: sessionid=abc123; Path=/
```

Example improved header:

```http
Set-Cookie: sessionid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
```

### Potential impact
Insecure cookie settings can increase the chance of:

- Session hijacking.
- Account impersonation.
- Cross-site request forgery.
- Unauthorised access after a user has logged in.

### Recommended remediation
All sensitive session cookies should use secure attributes:

```http
HttpOnly; Secure; SameSite=Lax
```

For highly sensitive workflows, `SameSite=Strict` may be appropriate, although usability should be tested. The application should also enforce HTTPS and regenerate session identifiers after login.

## Finding 4 — Excessive Permissions and Lack of Least Privilege

### Description
A weak access control implementation gives users more permissions than they need. For example, a standard user may be able to view administrative pages, access another user’s records, export sensitive data, or modify settings outside their role.

### Why this is vulnerable
Least privilege is a core defensive principle. If accounts have excessive permissions, the damage from account compromise or user error becomes much greater. Access control problems can also expose sensitive information through insecure direct object references, poorly protected API endpoints, or over-permissive roles.

### Example evidence to collect
For a real assessment, evidence could include:

- A standard test account accessing pages intended for administrators.
- API responses returning data belonging to other users.
- Role configuration showing broad default permissions.
- Screenshots comparing what different account types can access.

### Potential impact
Poor access control may allow:

- Unauthorised data viewing.
- Modification or deletion of records.
- Privilege escalation.
- Breach of privacy, compliance, or organisational policy.

### Recommended remediation
The system should implement role-based access control or attribute-based access control. Permissions should be denied by default and granted only where required. Access checks must occur on the server side, not only in the user interface. Regular permission reviews should be performed, especially for staff, contractors, administrators, and inactive accounts.

## Finding 5 — Publicly Exposed Development or Diagnostic Information

### Description
A weak implementation occurs when an application exposes debugging information, stack traces, internal server paths, framework versions, database errors, or development endpoints to public users.

### Why this is vulnerable
Information disclosure can help attackers plan more effective attacks. Even when the exposed information does not directly compromise the system, it may reveal software versions, internal file paths, database structure, environment variables, or implementation details.

### Example evidence to collect
For a real assessment, evidence could include:

- Public error pages showing stack traces.
- Debug mode enabled in a production environment.
- Exposed files such as `.env`, backup files, logs, or test endpoints.
- HTTP headers revealing unnecessary server or framework version details.

Example weak error message:

```text
DatabaseError: connection failed for user app_admin at /var/www/app/config/database.yml
```

Example safer error message:

```text
Something went wrong. Please try again later or contact support with error reference ID: 8F42A.
```

### Potential impact
Exposed diagnostic information may lead to:

- Easier vulnerability discovery.
- Targeted attacks against known software versions.
- Disclosure of internal infrastructure details.
- Leakage of sensitive configuration data.

### Recommended remediation
Production systems should disable debug mode and return generic error messages to users. Detailed logs should be stored securely and only accessible to authorised administrators. Sensitive files should not be deployed to public web directories. Server banners and unnecessary version headers should be removed or minimised where practical.

## Reflection

This activity demonstrates that security weaknesses are often caused by design and configuration choices rather than advanced technical flaws. The five weaknesses identified here affect different areas of cybersecurity: authentication, password management, session handling, access control, and information disclosure. Each weakness can increase the likelihood or impact of compromise, especially when combined with other issues.

The most important lesson is that secure systems need layered protection. MFA reduces reliance on passwords, strong password controls reduce credential attacks, secure cookies protect sessions, least privilege limits damage, and safe error handling reduces information leakage. These controls work best when implemented together as part of a defence-in-depth approach.
