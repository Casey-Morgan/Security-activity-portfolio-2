# B27 - Apply a Learned Cybersecurity Concept to a Real-World Problem

## Concept Applied

Least privilege access control.

## Overview

This entry applies a cybersecurity concept learned in the unit to a real-world problem. The concept chosen is **least privilege**, which means users, accounts, applications, and services should only receive the minimum access needed to perform their required tasks.

The real-world problem is excessive access in shared digital storage, such as a university project folder, cloud drive, or shared document workspace.

This activity focuses on defensive cybersecurity and safe access management. It does not involve unauthorised access or testing against systems without permission.

---

## Real-World Problem

Shared folders are commonly used for group projects, university work, clubs, workplaces, and family documents. However, these folders can become risky when permissions are too broad.

Common problems include:

- too many people having edit access;
- old members keeping access after they no longer need it;
- public sharing links being enabled;
- sensitive files being visible to the wrong people;
- users being able to delete or modify files accidentally;
- no clear separation between viewer, editor, and owner permissions.

This can lead to data leaks, accidental deletion, unauthorised changes, and privacy risks.

---

## Why Least Privilege Is Relevant

Least privilege helps solve this problem by limiting access to what each person actually needs.

For example:

| Person | Required Access | Reason |
|---|---|---|
| Project leader | Owner or manager access | Needs to organise folder and manage permissions |
| Group member writing content | Edit access | Needs to contribute to documents |
| Reviewer or tutor | View or comment access | Needs to review but not modify core files |
| Former member | No access | No longer needs the folder |
| Public users | No access | Project files should not be public |

This reduces the chance of accidental or intentional misuse.

---

## Applied Scenario

I applied the concept to a shared project folder scenario.

The goal was to design safer permissions for a folder used by a small student team.

The folder contained:

- project report;
- screenshots;
- research notes;
- code files;
- presentation drafts;
- submission documents.

Some files needed to be edited by team members, while others only needed to be viewed or reviewed.

---

## Access Control Plan

The following access control plan was designed.

| Resource | Owner | Editors | Viewers / Commenters | Public Access |
|---|---|---|---|---|
| Main project folder | Project leader | Current group members | Tutor if needed | Off |
| Final report | Project leader | Report writers | Tutor as commenter | Off |
| Evidence screenshots | Project leader | Current group members | None unless required | Off |
| Submission folder | Project leader | Project leader only | Group members as viewers | Off |
| Archive folder | Project leader | None | Current group members as viewers | Off |

---

## Implementation Steps

The following steps can be used to apply least privilege in a real shared folder environment.

### Step 1 - Review Current Permissions

Check who currently has access to the folder.

Look for:

- unknown users;
- old group members;
- public sharing links;
- people with unnecessary edit access;
- files shared outside the group.

### Step 2 - Classify Users

Sort people into categories:

```text
Owner
Editor
Commenter
Viewer
No access
```

### Step 3 - Remove Unnecessary Access

Remove users who no longer need access.

Examples:

- former members;
- accidental invitees;
- old email accounts;
- public links;
- anyone outside the project.

### Step 4 - Reduce Overly Broad Permissions

Change permissions where possible.

Examples:

```text
Editor -> Viewer
Editor -> Commenter
Public link -> Restricted access
```

### Step 5 - Protect Sensitive Files

Move sensitive files into a restricted folder.

Examples:

- private screenshots;
- credentials or configuration notes;
- personal information;
- final submission documents.

### Step 6 - Review Permissions Regularly

Permissions should be reviewed again after major project stages.

For example:

- before submission;
- after a member leaves;
- before sharing evidence;
- after the project is completed.

## Example Before and After

### Before Applying Least Privilege

```text
Main folder:
- Anyone with the link can view
- All group members can edit
- Former group member still has edit access
- Tutor has edit access
- Submission folder can be modified by everyone
```

### Risks

- public link may expose project work;
- former member can still access files;
- tutor does not need edit access;
- any group member can accidentally delete final submission files;
- too many users have unnecessary permissions.

### After Applying Least Privilege

```text
Main folder:
- Public link disabled
- Current group members have edit access only where needed
- Former member removed
- Tutor has comment or view access only
- Submission folder editable only by project leader
```

### Security Improvement

The folder is safer because access is limited, public exposure is removed, and sensitive files are better protected.

## Risk Reduction

Applying least privilege reduces several risks.

| Risk | How Least Privilege Helps |
|---|---|
| Data leakage | Removes public or unnecessary access |
| Accidental deletion | Limits edit and delete permissions |
| Unauthorised changes | Only approved users can edit |
| Privacy exposure | Sensitive files are restricted |
| Former member access | Old permissions are removed |
| Over-sharing | View/comment access replaces edit access where possible |

---

## Cybersecurity Analysis

Least privilege is effective because it limits the damage that can occur if a user makes a mistake or if an account is compromised.

For example, if a viewer account is compromised, the attacker may be able to see files but cannot edit or delete them. If an editor account is compromised, the damage could be greater. This is why edit access should only be given when necessary.

The concept also supports accountability. When fewer people have high-level access, it is easier to understand who is responsible for changes.

---

## Limitations

Least privilege reduces risk, but it does not remove all security problems.

Limitations include:

- users may still download and share files outside the folder;
- compromised owner accounts can still cause serious damage;
- permission settings may be changed later;
- users may accidentally share screenshots or copied content;
- access reviews require ongoing attention.

Because of these limitations, least privilege should be combined with other controls such as strong passwords, multi-factor authentication, backups, and user awareness.

---

## Recommendations

To maintain safer access control in shared folders:

1. turn off public sharing links unless absolutely required;
2. use viewer or commenter access instead of editor access where possible;
3. remove old members immediately when they no longer need access;
4. restrict sensitive folders separately;
5. review permissions before and after project submission;
6. enable multi-factor authentication on important accounts;
7. keep backup copies of important final files;
8. avoid storing passwords or secrets in shared documents.
