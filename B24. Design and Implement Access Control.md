# B24 - Design and Implement Access Control

## Topic

Role-Based Access Control (RBAC) for a small student project portal.

## Overview

This activity designs and implements a simple access control system. The system uses Role-Based Access Control, where each user is assigned a role and each role has a defined set of permissions.

Access control is a core cybersecurity concept because it decides who can access a resource and what actions they are allowed to perform. Strong access control helps prevent unauthorised access, accidental data exposure, privilege misuse, and unnecessary access to sensitive functions.

---

## Scenario

The access control system is designed for a small university project portal.

The portal has three roles:

| Role | Description |
|---|---|
| Admin | Manages users, files, reviews, and audit logs |
| Tutor | Reviews student submissions and views audit information |
| Student | Uploads and edits their own project work |

The goal is to make sure each user only has the permissions needed for their role.

---

## Security Principles Used

### Least Privilege

Users should only receive the minimum access needed to perform their task.

For example, a student should be able to upload their own work, but should not be able to manage users or view audit logs.

### Deny by Default

If a user or permission is not recognised, the system denies access.

This is safer than allowing access by default.

### Separation of Duties

Different roles have different responsibilities. Admins manage the system, tutors review work, and students submit work.

---

## Role Permission Matrix

| Permission | Admin | Tutor | Student |
|---|---|---|---|
| View project files | Yes | Yes | Yes |
| Upload project files | Yes | No | Yes |
| Edit project files | Yes | No | Own files only |
| Delete project files | Yes | No | No |
| Review submissions | Yes | Yes | No |
| Manage users | Yes | No | No |
| View audit logs | Yes | Yes | No |

---

## Access Control Design

The system follows this structure:

```text
User -> Role -> Permissions -> Access decision
```

Example:

```text
Chloe -> Student -> upload_project_files -> ALLOW
Chloe -> Student -> manage_users -> DENY
```

This design is easier to manage than assigning permissions individually to every user. If a new tutor joins, they can simply be assigned the Tutor role.

## Implementation Code

The following Python code implements the RBAC design.

```python
roles = {
    "admin": {
        "view_project_files",
        "upload_project_files",
        "edit_project_files",
        "delete_project_files",
        "review_submissions",
        "manage_users",
        "view_audit_logs"
    },
    "tutor": {
        "view_project_files",
        "review_submissions",
        "view_audit_logs"
    },
    "student": {
        "view_project_files",
        "upload_project_files",
        "edit_own_project_files"
    }
}

users = {
    "alice": "admin",
    "ben": "tutor",
    "chloe": "student"
}

def has_permission(username, permission, owns_resource=False):
    role = users.get(username)

    if role is None:
        return False

    permissions = roles.get(role, set())

    if permission == "edit_project_files" and role == "student":
        return owns_resource and "edit_own_project_files" in permissions

    return permission in permissions

test_cases = [
    ("alice", "manage_users", False),
    ("alice", "delete_project_files", False),
    ("ben", "review_submissions", False),
    ("ben", "manage_users", False),
    ("chloe", "upload_project_files", False),
    ("chloe", "edit_project_files", True),
    ("chloe", "edit_project_files", False),
    ("chloe", "view_audit_logs", False),
    ("unknown", "view_project_files", False)
]

for username, permission, owns_resource in test_cases:
    result = has_permission(username, permission, owns_resource)
    print(f"{username} -> {permission}: {'ALLOW' if result else 'DENY'}")
```

## Security Analysis

### Strengths

This access control design has several strengths:

- roles are clearly defined;
- users only receive permissions required for their role;
- admin, tutor, and student permissions are separated;
- unknown users are denied automatically;
- students can edit only their own project files;
- sensitive actions such as user management are restricted to admins.

### Why This Supports Least Privilege

The system avoids giving every user full access.

For example:

- tutors can review submissions but cannot manage users;
- students can upload work but cannot view audit logs;
- unknown users receive no access;
- only admins can delete files and manage accounts.

This reduces the possible damage if a lower-privilege account is compromised.

### Why Deny by Default Matters

The function returns `False` when a user is unknown or when a permission is not found.

This is safer because access must be explicitly granted. If the system is unsure, it denies the request.

---

## Limitations

This is a simplified educational implementation. A production system would need extra controls, such as:

- secure authentication;
- password hashing or passwordless login;
- session management;
- audit logging;
- database storage for users and permissions;
- protection against privilege escalation;
- input validation;
- multi-factor authentication for admins;
- regular access reviews;
- secure error handling.

---

## Possible Improvements

Future improvements could include:

1. storing users and roles in a database;
2. adding login authentication;
3. adding audit logs for denied requests;
4. adding multi-factor authentication for admins;
5. creating a web interface for the portal;
6. adding unit tests for every permission;
7. supporting temporary access permissions;
8. adding a review process for role changes.

---

## Defensive Cybersecurity Value

This activity demonstrates how access control can reduce security risk. A well-designed access control system helps ensure that users only access the resources they are authorised to use.

The design protects against:

- unauthorised access;
- overprivileged users;
- accidental file modification;
- students accessing tutor or admin functions;
- unknown users accessing project files.

## Reflection

This activity helped me understand that access control should be designed before writing code. The role permission matrix made it easier to decide what each role should be allowed to do.

The most important lesson was that access control is not just about allowing access. It is also about denying access when the user does not need it.

I also learned that small implementation details matter. For example, students can edit their own files, but not other users' files. This kind of rule is important in real systems because users may need partial access rather than full access.

Overall, this RBAC implementation shows how least privilege and deny-by-default can be applied in a simple cybersecurity design.
