# B17 - Implement and Evaluate a Current State-of-the-Art Cybersecurity Solution

## Solution Chosen

Passwordless authentication using a passkey-style public/private key challenge-response model.

## Overview

This activity implements a simplified version of a modern passwordless authentication approach. Real passkeys use public-key cryptography and are designed to reduce the risks caused by weak passwords, password reuse, phishing, and credential database breaches.

The implementation in this activity is an educational prototype. It demonstrates the core idea behind passkey-style authentication:

1. a user has a private key;
2. the server stores only the public key;
3. the server sends a random challenge;
4. the user signs the challenge using the private key;
5. the server verifies the signature using the stored public key.

No real account system or production authentication service was created.

---

## Why This Is a Current State-of-the-Art Solution

Traditional password authentication has several weaknesses:

- users may choose weak passwords;
- users may reuse passwords across websites;
- passwords can be stolen through phishing;
- password databases can be breached;
- attackers can attempt password spraying or credential stuffing.

Passkeys and passwordless authentication reduce these risks because the private key stays on the user's device and is not typed into a website. A phishing website cannot easily steal a reusable password because there is no password to steal.

---

## Security Goal

The goal of this implementation is to show how public-key authentication can verify a user without storing or transmitting a password.

The security objectives are:

- avoid storing plaintext passwords;
- avoid sending passwords over the network;
- verify identity using cryptographic signatures;
- make replay attacks harder by using a fresh random challenge;
- demonstrate why phishing-resistant authentication is stronger than password-only login.

## Prototype Design

### Components

| Component | Purpose |
|---|---|
| User private key | Secret key controlled by the user |
| User public key | Stored by the server |
| Challenge | Random value generated by the server |
| Signature | Proof created by signing the challenge |
| Verification function | Checks whether the signature matches the challenge and public key |

### Authentication Flow

```text
1. User registers.
2. The system generates a public/private key pair.
3. The server stores the public key.
4. During login, the server creates a random challenge.
5. The user signs the challenge with the private key.
6. The server verifies the signature using the stored public key.
7. If verification succeeds, the login is accepted.
```

---

## Implementation Code

The following Python code demonstrates the simplified authentication model.

```python
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes
from cryptography.exceptions import InvalidSignature
import os

# Registration stage
private_key = ec.generate_private_key(ec.SECP256R1())
public_key = private_key.public_key()

# Server creates a random challenge
challenge = os.urandom(32)

# User signs the challenge using their private key
signature = private_key.sign(
    challenge,
    ec.ECDSA(hashes.SHA256())
)

# Server verifies the signature using the stored public key
try:
    public_key.verify(
        signature,
        challenge,
        ec.ECDSA(hashes.SHA256())
    )
    print("Authentication successful")
except InvalidSignature:
    print("Authentication failed")
```

## Extended Test Code

This extended version tests successful authentication, replay with a different challenge, and an attacker using the wrong key.

```python
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes
from cryptography.exceptions import InvalidSignature
import os

def generate_user_key_pair():
    private_key = ec.generate_private_key(ec.SECP256R1())
    public_key = private_key.public_key()
    return private_key, public_key

def sign_challenge(private_key, challenge):
    return private_key.sign(
        challenge,
        ec.ECDSA(hashes.SHA256())
    )

def verify_signature(public_key, challenge, signature):
    try:
        public_key.verify(
            signature,
            challenge,
            ec.ECDSA(hashes.SHA256())
        )
        return True
    except InvalidSignature:
        return False

# Legitimate user registration
user_private_key, user_public_key = generate_user_key_pair()

# Attacker key pair
attacker_private_key, attacker_public_key = generate_user_key_pair()

# Test 1: Correct user signs correct challenge
challenge_1 = os.urandom(32)
signature_1 = sign_challenge(user_private_key, challenge_1)
test_1 = verify_signature(user_public_key, challenge_1, signature_1)

# Test 2: Replay attempt using old signature on a new challenge
challenge_2 = os.urandom(32)
test_2 = verify_signature(user_public_key, challenge_2, signature_1)

# Test 3: Attacker signs challenge with wrong private key
challenge_3 = os.urandom(32)
attacker_signature = sign_challenge(attacker_private_key, challenge_3)
test_3 = verify_signature(user_public_key, challenge_3, attacker_signature)

print("Test 1 - Correct user:", "PASS" if test_1 else "FAIL")
print("Test 2 - Replay attempt blocked:", "PASS" if not test_2 else "FAIL")
print("Test 3 - Wrong key blocked:", "PASS" if not test_3 else "FAIL")
```

## Security Analysis

### Strengths

This implementation demonstrates several strong security properties:

- the server does not store a password;
- the user does not type a reusable secret during login;
- the authentication challenge is random;
- the signed response is only valid for the specific challenge;
- attackers cannot authenticate without the correct private key;
- replaying an old signature does not work against a new challenge.

### Weaknesses and Limitations

This is only a simplified educational prototype. A production passkey system would need additional security controls, including:

- secure private key storage in hardware or the operating system;
- origin binding to prevent phishing websites from using the credential;
- user verification such as biometrics or PIN;
- secure account recovery;
- protection against device theft;
- server-side session management;
- rate limiting and monitoring;
- proper registration and credential lifecycle management.

## Comparison with Password-Based Login

| Feature | Password Login | Passkey-Style Authentication |
|---|---|---|
| Secret typed by user | Yes | No |
| Server stores password verifier | Yes | Public key only |
| Resistant to phishing | Weak | Stronger |
| Risk from password reuse | High | Low |
| Replay resistance | Depends on implementation | Strong when fresh challenges are used |
| User experience | Often requires remembering passwords | Can use device unlock methods |

## What I Learned

This implementation helped me understand why public-key authentication is stronger than traditional password-based login. The private key never needs to be sent to the server, and the server can still verify the user by checking a digital signature.

The evaluation also showed why random challenges are important. When the server uses a new challenge each time, an old signature cannot simply be copied and reused.
